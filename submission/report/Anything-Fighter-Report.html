ANYTHINGFIGHTER01 · Summary & idea

Executive summary

A fighting game whose roster is the whole world

Anything Fighter is a browser fighting game where the player supplies the characters. Point a phone at a mug, a sneaker or a rubber duck, press Forge, and a chain of Aholo services turns that single photo into a full-body fighter concept, a textured PBR mesh, a humanoid skeleton and a set of retargeted fight moves. A few minutes later the new fighter is in the roster, ready to fight the CPU, a friend on the same keyboard, or any other fighter in the gallery, inside an Aholo-generated 3D world.

Aholo is not an add-on here. It is the content pipeline: every fighter, every 3D arena, the room-scan stage and every KO poster comes from Manycore's tools, called through the official @manycore/aholo-sdk-* TypeScript packages. Everything else is built around them so the player only sees photo in, fighter out.

The problem

Fighting games live or die by their roster, and every character normally costs weeks of concept art, modelling, rigging and animation. Players can pick a costume, but never bring their own character, and certainly not the coffee mug on their desk.

Generative 3D has made single assets cheap, but a playable character needs much more than a mesh: it needs a humanoid body, a skeleton, animation that fits that skeleton, and a stage to fight in. Stitching that together by hand is still a studio job.

The idea

Use Aholo's 3D AI stack as a character and stage factory that runs while the player waits:

  • Lux3D re-imagines any object as a humanoid fighter, builds the mesh, rigs it and retargets preset fight moves.
  • SpatialGen generates themed 3DGS arenas from text; Reality rebuilds the player's room from a phone video.
  • Aholo Viewer renders those splats live behind the fight; RenderCloud path-traces a KO poster.

The result is a game where the roster grows with every photo, and every player has a fighter nobody else has.

Stages as named in lib/aholo.ts. Poster and print export are non-fatal: a failure, or a poster taking over 8 minutes, moves the job on.

  • Concept. Lux3D multimodal-to-image turns the object photo into a full-body humanoid fighting-game character in a T-pose, so that a mug can actually take a skeleton.
  • Mesh. Lux3D image-to-3D, G1-Turbo, PBR textures, GLB output, requested as a 1.8 m character (customSize: 1800).

  • Rescue path. If Lux3D answers RIG_ELIGIBILITY_FAILED, the app re-rigs once on a normalised 1.8 m copy of the same mesh. If it still refuses, the fighter ships freestyle (unrigged Lux3D mesh, procedural moves) instead of dead-ending.

ANYTHINGFIGHTER04 · Architecture

System design

Browser · Next.js on Vercel · Aholo cloud

Solid arrows: HTTP calls between the browser and the app's routes; orange arrows: calls into Aholo through the official SDKs (RenderCloud via the sdk-core gateway client). The API key exists only on the server; the browser only ever receives a short-lived OUS upload token.

How the integration follows Manycore's guidance

  • SDKs, not hand-written HTTP for Asset, World and Lux3D, as Manycore's llms.txt recommends. SDK errors (RateLimitError, BusinessError…) are mapped to app errors; 429 / 5xx / network are retried on the next poll.
  • Async create → poll, exactly as the World and Lux3D APIs are designed, but one step per request (page 11).
  • Visible in the product: a "Powered by Aholo" strip on the forge panel, the live forge page (lights up per stage), the select screen, the VS splash and every gallery card lists the services that actually built that fighter.
  • No key, still demoable: without an API key every pipeline runs in a clearly labelled mock mode.

Stack: Next.js 16 (App Router, TypeScript, Tailwind 4) · React 19 · React Three Fiber + drei + three.js · Zustand · @manycore/aholo-sdk-asset / -world / -lux3d / -core · @manycore/aholo-viewer · gltf-transform + meshoptimizer · sharp · MediaPipe Tasks Vision (face gate) · Vercel Functions, Runtime Cache and Blob · WebAudio-synthesised sound.

What we learned from Lux3D

Asking multimodal-to-image for a full-body humanoid in a T-pose is what makes rigging work on non-humanoid objects. Requesting a 1.8 m character (instead of letting size be predicted from the object, which sized a sneaker like a 30 cm figurine) was the fix for rig eligibility failures.

Rig & retarget findings

The rig is a Mixamo-named 52-joint skeleton. Each retargeted clip GLB repeats the full textured mesh (~22 MB), so the app strips it to skeleton + clip (≈0.05–0.1 MB) and converts fighter textures to WebP (21.8 MB → 3.4 MB in the measured run). The 85 official presets include no kick, so Melee_Hook stands in.

How the KO poster is made

The app bakes a mid-jab pose from the fighter's own punch clip into a static mesh, uploads it through OUS, runs RenderCloud mesh ingest, builds a USD scene (studio backdrop + lights, lib/poster-usda.ts) and submits an offline path-traced render job. The poster is shown on the VS splash, in the gallery and on the downloadable KO card.

ANYTHINGFIGHTER06 · Arenas: SpatialGen, Reality, Viewer

3D worlds

Fight in an AI world, or in your own room

Rooftop Dojo at Sunset (SpatialGen 3DGS world) · Mug Shot vs Quack Attack.
My Room (scan) (Aholo Reality reconstruction) · Sole Survivor vs Mug Shot.

SpatialGen arenas

Three themed worlds were generated from our own text prompts with world.generations.create: Kitchen Colosseum, Toy Shop at Midnight and Rooftop Dojo at Sunset. Each produces a 3DGS splat and a panorama; the panorama becomes the stage-select cover and the fallback backdrop. Finished worlds appear as playable stage cards automatically.

Aholo Reality: "Fight in your room"

The stage select has a builder card: record a slow 10–20 s loop (or choose a video, or 20+ photos), and Aholo Reality rebuilds the room as a playable splat arena (Flash quality, ~20 credits). Files upload directly from the browser to Aholo OUS; the server only mints the upload token and calls world.reconstructions.create. Reality worlds use the official WorldDetail.cover as their card image.

Stage select with the always-visible Reality room builder above the built-in Neon Ring and SpatialGen cards.

Aholo Viewer under React Three Fiber

The Aholo Viewer is its own WebGL engine and cannot live inside an R3F canvas, so the game stacks two canvases: the Viewer renders the splat underneath, and a transparent R3F canvas draws the fighters on top, with the Viewer camera synced from the fight camera every frame.

Making splats fight-ready. lib/splat-fit.ts decodes each SPZ, finds the floor band and the largest floor rectangle, aims the camera down the room's long axis and scales the world so fighters stand on the floor. New worlds are auto-fitted server-side. If a splat cannot load on a device, the fight swaps to the world's panorama, then to the Neon Ring, and keeps going.

Fun & engagement

A real fighting game, not a model viewer

Kitchen Colosseum (SpatialGen world) · Mug Shot vs Quack Attack, 1P vs CPU. Before each fight a VS splash slams in both RenderCloud posters and tags each fighter with how it was built (e.g. "Aholo Lux3D starter · retargeted clips").

Move set

Plus jump and crouch: highs whiff over a crouch; any clean hit on an airborne fighter is an anti-air knockdown. Damage scales down over long combos; counter-hits deal +20 %.

Modes & feel

  • 1P vs CPU with Easy / Normal / Hard. The CPU drives the same inputs as a player: it extends strings, punishes whiffs, parries (Hard), jumps in, sweeps and anti-airs.
  • 2 players on one keyboard, and practice (infinite time, the partner never attacks), shown while your fighter forges.
  • Any fighter vs any fighter: starters, your forged fighter, or one from the gallery ("Fight as" / "Fight vs").
  • Arcade presentation: screenpack-style life bars with a lagging damage layer, super meter ring, round timer, combo and hit callouts, hit sparks, screen shake, haptics on phones, K.O. / TIME! stamp, victory panel.
  • Freestyle fighters still fight: if Lux3D can't rig a mesh, procedural motion (and a 3-bone arm rig for T-posed meshes) performs every move.
  • After the fight: rematch, a 1600×900 KO card with the RenderCloud poster, and a recorded clip (MP4 or WebM) to share manually.

The rules are covered by npm run test:sim: 18 deterministic checks (strings, scaling, jump arc, crouch, lows, overheads, anti-air, special, super).

ANYTHINGFIGHTER09 · Privacy & safety

Responsible design

Snap anything, but protect the people in it

"Snap anything" invites photos of people, so the design assumes that will happen. Nothing a player uploads becomes public unless they explicitly ask, attest and pass the face gate, and anyone can flag what does.

SafeguardHow it works
Private by defaultA player's source photo is never served or listed unless they opt in; thumbnails come from the Lux3D concept or the RenderCloud poster.
Opt-in + consentSharing needs a checkbox and an attestation that the uploader has the right to share and the photo shows no identifiable person without their consent. The choice is recorded at forge time; older forges are never published retroactively.
Face gateAholo's published APIs have no face-detection or moderation endpoint, so the browser runs MediaPipe face detection. A face, or any model error, keeps the photo private (fail closed); the forge itself still runs.
Report + moderationEvery card has a Report dialog; reports land in an owner-only queue at /moderation that can hide or unpublish a card.
One-time delete linkWhen a forge finishes, its creator gets a one-time "Remove from gallery" control backed by a signed token.
Instant takedownShared photos are served with private, no-store, so a removal takes effect immediately rather than lingering in caches.
No leaked URLsJob responses strip signed Aholo URLs (including the uploaded photo); the durable Blob store is private.
Spend guardLive forges are capped per IP and globally per Africa/Lagos day; past the cap the forge continues as a clearly labelled demo forge (no credits) instead of failing.
SecretsThe Aholo API key lives only in server-only modules; the browser gets at most a short-lived OUS upload token. Without a key the whole app runs in labelled mock mode.
Forge form on a phone (live site): sharing is off by default and needs the consent attestation.
Why the face check runs in the browser. We looked for a moderation or face-detection capability in Aholo's published OpenAPI (Asset, World, Lux3D, RenderCloud, Spatial Understanding) and found none, so the check runs on the player's device before anything can be shared. It only gates public sharing; the photo still goes to Lux3D to build the fighter, and stays private.

ANYTHINGFIGHTER10 · Engineering challenges

Completeness

Problems we hit, and how we solved them

ChallengeSolution
Long async Aholo jobs vs short serverless requestsPoll-driven state machine. Each GET /api/pipeline/[id] performs at most one transition: one SDK create or one tasks.retrieve. The SDKs' blocking waitFor helpers are deliberately not used inside requests, so no function waits on a multi-minute job. An advance lock (150 s) stops a hung function from wedging a job.
Forge froze on mobile ("Failed to fetch")The forge page's poll is a self-rescheduling loop with exponential backoff, a 75 s request abort, and immediate resume on tab focus, visibility change or network return. Transient errors (429, 5xx, network, timeouts) retry silently; players see plain-language messages with a Retry.
Room scans vs Vercel's ~4.5 MB request body limitA real scan video is ~18 MB, so posting it through a serverless function could never work in production. Now the server mints a short-lived OUS token with the official asset SDK, the browser uploads straight to Aholo OUS with the official OusHttpClient (single / multipart, MD5, status poll), and the server calls world.reconstructions.create with the asset URLs. The API key never leaves the server.
Lux3D refused some rigs (RIG_ELIGIBILITY_FAILED)Request 1.8 m characters; on refusal, re-rig once on a normalised copy of the same mesh (no new mesh credits); if it still fails, ship the fighter freestyle with procedural animation rather than dead-ending the forge.
Heavy rig / clip outputsEach ~22 MB retarget GLB repeats the mesh; the app downloads one clip per poll and strips it to skeleton + clip with gltf-transform; fighter textures go to WebP.
Aholo result URLs expire (~2 h)Everything needed later is rehosted. Finished world splats are served through a redirect to a freshly signed Aholo URL (no multi-MB rehosting).
Ephemeral serverless storageStarters ship in the deployment; jobs use Runtime Cache (2 MB items chunked) + /tmp; finished live fighters are saved as one private Vercel Blob pack. Missing models are hidden from the roster, and a SafeModel boundary swaps a failing model or clip for procedural moves.
Aholo Viewer + Next.js bundlingBundling the Viewer broke its Blob-URL workers; it is vendored to public/vendor and loaded with a non-bundled import(). Splat URLs are made absolute for the worker; each URL is retried with a same-origin proxy as a fallback.
One world job per account, no cancel API/api/arenas reports the account queue, refuses new world jobs while it is busy, and flags jobs stuck at 0 % for 90+ minutes. Fights always have Neon Ring and the Aholo Viewer sample splat available.
Limited hackathon creditsPer-IP and global daily forge limits; past the cap the forge continues in labelled mock mode, so judges never hit a dead end and the budget is protected.

How we tested it

  • npm run test:sim: 18 deterministic gameplay checks run offline (no credits).
  • npm run test:durable: the Blob pack store against a mocked Blob API, including cache headers and the health probe.
  • Lint and production builds; production checks of /api/health, photo privacy (private photos return 404) and cache headers.
  • Scripted browser drivers playing full fights with keyboard and real touch-pointer events, including Android emulation (412×915, touch, 4× CPU throttle) against the Hard CPU.
  • Live end-to-end forges through the official SDKs on production, kept few on purpose to protect the credit budget.
  • Mock mode lets the whole UI be exercised without spending credits.
